# Solace-AI MVP Remediation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development, as adapted in section 5 of this plan (no git commits, parallel dispatch of file-disjoint tasks, AGY as a third reviewer). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the Solace-AI backend releasable as the confirmed "Pilot + enterprise basics" MVP. Close all 345 in-scope entries of the issue register, each proven by a test that fails before the fix, then pass the release gate twice on the strict production profile.

**Architecture:** Six barrier waves (W0 to W5) over 18 workstreams with disjoint file ownership, executed in parallel in one working tree with commit-free checkpoints. Contention is removed by seams rather than by scheduling: one runtime bootstrap that every service `main.py` adopts once, pre-allocated Alembic slot revisions, single owners for compose, the environment contract and the seven event bridges, a one-time user-service split, one clinician-reviewed crisis lexicon for all five detectors, and short-lived on-behalf-of service tokens so no user credential enters LangGraph state. Waves follow risk: build, migrate and boot; the crisis path; the chat turn and durable state; privacy controls; the enterprise basics; then residual defects and the release gate.

**Tech Stack:** Python 3.12, FastAPI, LangGraph 1.0 with a Postgres checkpointer, PostgreSQL 16 with row-level security, Kafka with a transactional outbox, Redis, Weaviate, Caddy, Docker Compose, Alembic, a uv hash-pinned lock, pytest with testcontainers; Anthropic models on AWS Bedrock for LLM features (D-04), Amazon SES for clinician alerts (D-12), SOPS + age for secrets (D-07), AWS us-east-1 (EC2 via SSM, S3 with KMS) for the release gate and the pilot (D-25).

**Spec:** [docs/MVP-ISSUE-REGISTER.md](../../MVP-ISSUE-REGISTER.md) is the binding issue list and records the confirmed scope; [docs/MVP-BUG-REVIEW.md](../../MVP-BUG-REVIEW.md) is its verification record. Every task is in one of the 18 workstream plans in [2026-10-18-mvp-remediation/](2026-10-18-mvp-remediation/). Interface contracts and file ownership are in [00-interfaces-and-ownership.md](2026-10-18-mvp-remediation/00-interfaces-and-ownership.md).

**Tracking:** [docs/mvp/README.md](../../mvp/README.md) is the hub. It links [DECISIONS.md](../../mvp/DECISIONS.md) (owner decisions and sign-offs), [TRACKER.md](../../mvp/TRACKER.md) (per-task status and the barrier log), [OPEN-ITEMS.md](../../mvp/OPEN-ITEMS.md) (owner actions, sign-offs, risks) and [LOG.md](../../mvp/LOG.md) (dated history). Those files are the persistent record; this plan is the method.

## Global Constraints

- Python 3.12 only. Local interpreter: the program venv D:\tmp\mvp-exec\venv\Scripts\python.exe (D-20), created at W0 entry from the anaconda 3.12.3 interpreter with --system-site-packages and called by full path from the PowerShell tool (the bare 'python' shim and the Bash tool hook are broken). Nothing is ever installed into anaconda. Images use python:3.12-slim pinned by digest from W0. No runtime or test dependency is added except through WS-01's lock.
- Unit tests use exactly this PowerShell command, one pytest process per suite: $env:PYTHONPATH="D:\Repo\Contextual-Chatbot;D:\Repo\Contextual-Chatbot\src"; $env:ENVIRONMENT="test"; & D:\tmp\mvp-exec\venv\Scripts\python.exe -m pytest <suite> -o "addopts=" -p no:logging -q. Suites: each tests/<dir> (solace_events, solace_security, solace_infrastructure, solace_common, solace_testing, integration, alignment, security, migrations, scripts, system, config_service, plus the new bootstrap, build, deploy, contracts, clinical), tests/test_syntax_and_imports.py, infrastructure/api_gateway/tests and each services/<svc>/tests. Baseline 5,377 passed in anaconda, re-recorded per suite in the venv at W0 entry; counts are compared at every barrier and a drop needs a ledger Ruling.
- Real-infra tests carry marker realinfra (testcontainers, tests/realinfra/<ws-slug>/) or e2e (compose stack, tests/e2e/, project solace-e2e-<lane>, Docker-assigned 127.0.0.1 ports). At most 2 lanes run them at once; stacks are torn down with their volumes. At barriers SOLACE_REQUIRE_REALINFRA=1 is set, so a skipped realinfra or e2e test fails.
- No git commit, branch, worktree, stash, reset, checkout, clean or push, and the real git index is never touched. Every task starts and ends with D:\tmp\mvp-exec\tools\checkpoint.ps1 -Label "<task>:base" / "<task>:head"; review packages come from review-package.ps1; rollback only via rollback.ps1. Nobody commits during the program, the owner included (D-17); each barrier tree is also exported with git archive to a zip outside the repo.
- Implementers edit only their task's declared files, all inside their workstream's owned_paths; contended files follow the shared_files protocols. Work needed in another workstream's files is a supporting task in that workstream's lane citing the issue id; the issue-owning workstream writes the acceptance test and closes the issue only when every part has landed. New test files are named test_mvp_<id>_<slug>.py; an existing test file is edited only by the owner of the code under test.
- TDD in six steps per task: write the failing test; run it and record RED for the defect's reason; write the minimal fix; run to GREEN; run the owning suite; checkpoint. A defect test that passes before the fix is a finding against the task. Test names or docstrings cite the MVP id they prove.
- Strict environments are ENVIRONMENT in {staging, production} (solace_infrastructure.runtime.is_strict_environment); the pilot runs production. In strict envs a missing or failing declared dependency (secret, Postgres, Redis, Kafka/event plane, codec, audit store, peer URL, LLM configuration when egress is approved) fails startup; no in-memory store or localhost default stands in for PHI, crisis events, sessions, tokens, rate limits, the outbox or the DLQ. Development/test fallbacks log WARNING and make /ready 503. No guard is keyed on 'production' alone.
- Lifespans contain no try/except that swallows a platform-component failure. /ready reflects real dependency state; Docker healthchecks and Caddy use /live; a degraded agent result is never reported as success.
- Schema changes go only through the Alembic slot files (IF-03), as phase-A tasks run one at a time in a per-wave schema lane. Services connect as solace_app and run no DDL. RLS policies use NULLIF(current_setting('app.current_user_id', true), '')::uuid; RLS tables are accessed only through ConnectionPoolManager.acquire()/transaction(); work without a request runs inside acting_as_user(user_id).
- PHI rules: never log, emit, cache, return in errors, or put into metric labels any message text, symptoms, diagnoses, names, emails, phone numbers, tokens or secrets. Events carry ids and category codes only. PHI columns go through solace_security.phi_codec with the owner as AAD. No PHI goes to a third party except via Anthropic models on AWS Bedrock under the AWS BAA (D-04) with caching off, or in clinician alerts under D-12. Tests use synthetic data only. Never print .env or generated secret values in tool output, reports or tests.
- Client-visible errors never include str(exception), SQL or stack traces; bodies follow {error:{code,message,request_id}} per IF-01.
- Crisis invariants: in-band resources never depend on the LLM, downstream services, Kafka or the database; fusion is max-only and no change may lower a lexicon-derived level; every HIGH/CRITICAL detection writes a durable outbox row before the response returns, or counts and alerts a publish failure; pages are coalesced per IF-09; changes to the lexicon, thresholds or escalation behaviour need the D-05/D-06 record and must keep tests/clinical green.
- Inter-service calls use IF-04 tokens only (obo for user-scoped calls, forwarded inbound headers for same-user downstream calls); user JWTs are never forwarded and no credential enters LangGraph state. Every hop propagates X-Request-ID, X-Correlation-ID and X-Turn-ID, has an explicit timeout, and retries a POST only with an Idempotency-Key the provider honours.
- Environment variable names follow IF-02; a new setting is requested as an env-registry entry from WS-03 in the same wave and enforced by tests/deploy/test_env_contract.py. /metrics, /docs, /openapi.json, /status and /api/v1/internal/* are never routed by Caddy.
- Latency budgets: crisis screen < 5 ms per message; safety-service check 2 s (on timeout the local result stands and 'degraded' reports it); per-hop agent timeout 8 s; turn deadline 20 s; crisis resources in the response within 3 s in E2E; crisis alert delivery within 60 s in E2E.
- Models and reviews: Sonnet 5.5 implements well-specified standard tasks. Every safety-critical or security-critical task gets an Opus 5.5 implementer, an Opus 5.5 reviewer and an AGY adversarial review; design-heavy tasks (IF-01, IF-04, IF-05, IF-07, IF-09, IF-13, IF-14, IF-16, the harness) are Opus 5.5. Fix rounds 1-3 resume the implementer; rounds 4-5 use a fresh Opus 5.5. Implementers never spawn subagents. AGY runs only through the gemini plugin MCP with engine agy, on an exported snapshot, never on the real repo.
- Each wave runs phase A first: platform lanes touching src/**, services/shared/**, migrations/**, infrastructure/**, the seven event_bridge.py files, compose, CI, build or requirements (this includes service-owned slot files, src/solace_clinical and src/solace_infrastructure/gdpr). Phase B (service lanes) follows. At most 6 implementers run concurrently; full regression runs only at barriers.
- An interface is frozen at the start of the wave that first uses it. Any change needs a ledger Ruling naming every consumer workstream, and the consumers' tests are updated in the same wave.
- Tests never call real LLM, SMTP, SMS or OAuth providers; only the fake LLM, mailpit and the stub OIDC provider. Installing packages beyond D-20 or anywhere except the program venv, pulling unpinned images, provisioning cloud resources, pushing, or touching anything outside the working tree and D:\tmp\mvp-exec requires owner approval (stop condition).
- Out of scope, do not edit: services/config_service/** beyond removing it from compose; Kong modules beyond import decoupling; ClickHouse paths; the RBAC/ABAC policy engine; HA/DR, horizontal scaling and load/chaos work. Post-MVP ids MVP-333 to MVP-343 are not scheduled.
- When a task completes, its Status in docs/mvp/TRACKER.md is set to done (python docs/mvp/tools/mvp_docs.py set ...); register statuses are derived from the tracker (an entry is fixed when every task covering it is done). docs/MVP-ISSUE-REGISTER.md is re-rendered by the controller at each wave barrier and is not owned by any workstream; docs/mvp/** is controller-only and excluded from scope-breach checks.
- Execution starts only on the owner's "go". Until then nothing in the repo changes except these plan documents and the register.
- Secrets use SOPS + age (D-07); no AWS Secrets Manager or Parameter Store holds secrets. If any AWS secrets work ever arises, load the aws-secrets-manager skill first and use `{{resolve:secretsmanager:...}}` references through asm-exec; no agent calls `get-secret-value` or `batch-get-secret-value`, and no secret value or age private key enters a prompt, report, log or the repo.
- Decisions are recorded in docs/mvp/DECISIONS.md, the live record; section 3 is the snapshot of 2026-10-19. A changed decision is a ledger Ruling plus an entry in DECISIONS.md and docs/mvp/LOG.md before any task acts on it.
- AWS resource names and descriptions use hyphens, never em dashes. AWS work prefers the AWS MCP server and infrastructure as code (CloudFormation in infrastructure/aws-staging).

## 4. Waves, phases and tasks

A wave ends at a barrier (section 5.5). Inside a wave, phase A tasks touch platform paths (`src/**`, `services/shared/**`, `migrations/**`, `infrastructure/**`, `deploy/**`, `docker/**`, the seven `event_bridge.py` files, compose, CI, build and requirements files) and run first. Phase B tasks touch service paths and start when phase A is done. The tables list each phase's tasks by dependency level: a task needs only tasks from earlier levels of its phase (and anything from earlier phases and waves). Tasks in one level run concurrently when their files and suites do not overlap, as section 5.3 describes.

### 5.2 Per-task loop (TDD plus subagent-driven development)

1. **Brief.** Run `extract-brief.ps1 -Task <id>`, then run `checkpoint.ps1 -Label "<id>:base"` and record `start base=<tree>` in the ledger.
2. **Dispatch the implementer.** Use the task's `Implementer model` (Sonnet 5.5 or Opus 5.5), always set explicitly. Use the skill's `implementer-prompt.md` with these changes:
   - "commit" becomes "run checkpoint.ps1 and report the tree id";
   - the implementer must edit only the task's declared files;
   - it must follow the six TDD steps in order, and the report must show the RED output from Step 2;
   - implementers never spawn subagents.
3. **Check scope.** Run `checkpoint.ps1 -Label "<id>:head"`, then `review-package.ps1 -Paths <declared files>`. Any changed path that no running task declared is a scope breach: roll it back with `rollback.ps1`, or rule on it in the ledger.
4. **Review** according to the task's `Review` class (see 5.4). The reviewer receives the brief, the report and the package. It returns spec compliance and quality verdicts.
5. **Fix loop**, as in the skill: at most 5 rounds. Rounds 1-3 resume the same implementer; rounds 4-5 use a fresh Opus 5.5 implementer. Each round ends with a scoped re-review of the fix diff, using `review-package.ps1` from the previous head tree. At the cap, adjudicate with ledger rulings.

The RED step is not optional. A defect-fix test that passes before the fix is a finding against the task, and the task is not done until the test proves the defect.

### 5.3 Parallel execution in one working tree

The owner's rule is no commits and no worktrees, so every implementer works in the same tree. Parallelism comes from running only tasks that cannot disturb each other:

- **Ready tasks.** Inside a wave and phase, a task is ready when every task it depends on in that wave and phase is complete. Dependencies in earlier waves, and phase-A dependencies of phase-B tasks, are complete by construction.
- **Mutual exclusion.** Each task has mutex keys: every file it creates or modifies, plus the suite of every file it creates, modifies or tests (`services/<svc>`, `services/shared`, `src/<pkg>`, `tests/<suite>`, `tests/realinfra/<slug>`, `tests/e2e/<x>`, `infrastructure/<x>`, and `migrations` as one key). Two tasks that share a key never run at the same time, because each runs its owning suite as its regression step. `D:\tmp\mvp-plan\schedule_dag.json` lists each task's keys, same-phase dependencies and chain height. `check_plans2.py` regenerates it from the plan files.
- **Dispatch.** The controller keeps up to 6 implementers busy, with at most 2 on real-infra tasks (Docker resources). Among the ready tasks whose keys are free, it picks the longest remaining dependency chain first, then blockers before highs, then safety-critical before security-critical before standard.
- **Phases.** Platform tasks run first in each wave (phase A); service tasks start when phase A is done (phase B). A task is phase A if it touches a platform path as the Global Constraints define it: `src/**`, `services/shared/**`, `migrations/**` (service-owned slot files included), `infrastructure/**`, `deploy/**`, `docker/**`, the seven `event_bridge.py` files, compose, CI, build or requirements files. A task is phase B if it touches only service paths. A task that touches only tests, scripts or docs follows its same-wave dependencies (phase B if any of them is phase B). Every suite imports the shared packages, so a half-edited platform file must never be under a service task's tests.
- **Phase-A cross-talk.** Phase-A tasks can still see each other's half-edited shared packages. If a phase-A implementer's suite fails inside a file that another running task owns, it waits for that task's next checkpoint and re-runs before treating the failure as its own. If this happens twice for the same pair of workstreams, the controller adds a mutex key between them for the rest of the phase.
- **Test scope.** During a task, an implementer runs only its own tests and the owning suite. The full regression across all suites runs only at the wave barrier.
- **Pre-dispatch check.** Before dispatching a task, the controller confirms that its mutex keys are disjoint from every running task's keys. After each task it checks the package's "All changed paths" section for edits outside the task's declared files.

### 5.5 Wave barrier

A wave is done only when all of these hold, in this order:

1. Every task in the wave has a `complete` ledger line.
2. **Full regression is green.** Every suite runs in its own pytest process (section "Global Constraints" has the command). Test counts are compared with the previous barrier, and any drop in count is investigated.
3. **The wave's real-infra acceptance tests are green** (listed in the wave's exit criteria in section 4).
4. **Wave package.** Run `review-package.ps1 -Base <wave-start tree> -Head <wave-end tree> -Name wave-N`.
5. **Bug-finding rounds** (section 5.6) until a round is dry.
6. The register is re-rendered with the new statuses, and the wave summary is appended to the ledger.

### 5.6 Bug-finding rounds

The input to round 1 is the wave package. The input to each later round is the fix diff from the previous round.

1. **Hunt** in parallel:
   - Sonnet 5.5 hunters, one per changed area (at most 4). They are told what this wave fixed, so they look for regressions, missed paths, and new defects introduced by the fixes.
   - One AGY adversarial review on the exported snapshot.
2. **Verify.** Each finding goes to a Sonnet 5.5 voter and an Opus 5.5 voter. On a split, an Opus 5.5 tie-breaker casts a third vote. A majority refute removes the finding.
3. **Fix.** Each confirmed finding becomes a register entry (the next MVP-xxx id) and a fix task `WS-NN.F<k>` in the owning workstream, dispatched like any other task. It goes through the full per-task loop (TDD, review).
4. **Repeat** until a round confirms nothing new, with a cap of 3 rounds per wave. Findings still open at the cap are ruled on in the ledger and scheduled into the next wave.

### 5.7 Stop conditions

The controller does not pause between tasks or waves. It stops and asks the owner only for:

- an irreversible or destructive operation;
- a security-sensitive action;
- a side effect outside the working tree that norms say to ask about first (installing packages system-wide, pushing, publishing, provisioning cloud resources);
- a plan defect so deep that every path forward is a guess.

The venv bootstrap at W0 entry (section 5.0) is approved by D-20. Installing anything into anaconda or system-wide is a stop. AWS provisioning needs the deployer policy attached to the existing user MedCodex-Local (D-25); if it is still unattached at W5 entry, the release gate is a stop. No AWS call ever reads a secret value (D-07 uses SOPS).

Every other ambiguity becomes a ledger `Ruling:`. At the end, all rulings are reported to the owner in order.

## 7. Test strategy

Four tiers, each with a fixed home and marker.

1. Unit and in-process: the existing 5,377 tests plus a RED-first test for every defect, run with the global command in one pytest process per suite; mocks only at process boundaries. The clinical phrase set (tests/clinical, marker clinical) and hypothesis tests of normalize_text/screen_text run in every barrier regression against every detector.

2. Contract (marker contract, IF-20, tests/contracts): for every orchestrator-to-service call, therapy-to-memory, the client REST/WS protocol and every event producer/consumer pair, the consumer's contract file is verified against the provider's real FastAPI app and pydantic schemas in-process, catching URL, credential, field-name, enum-case and status drift without containers. Event contracts start in W1, REST contracts in W2.

3. Real-infra component (marker realinfra, tests/realinfra/<ws-slug>/, IF-19 fixtures on testcontainers): postgres:16 migrated by the real scripts.db.migrate as solace_migrator and accessed as solace_app under RLS; redis:7 with a password; cp-kafka 7.5 through aiokafka; mailpit; the fake LLM. Every workstream uses it for repository-vs-schema round trips with ciphertext checked in raw SQL, RLS denial, event-plane crash/redelivery/poison/reaper/idempotency semantics, per-store erasure, refresh-token rotation and audit-chain concurrency. tests/migrations/test_chain_real_pg.py runs upgrade head, downgrade base, upgrade head on every slot change.

4. E2E acceptance (marker e2e, tests/e2e, WS-05): the real images through docker-compose.yml + docker-compose.test.yml (dev) or + docker-compose.prod.yml (strict, ENVIRONMENT=production or staging) with per-run generated secrets, fake LLM, mailpit and a stub OIDC provider, on Docker-assigned 127.0.0.1 ports, with client traffic through the edge Caddy so proxy-hop logic is exercised. Tests use only public endpoints, create users through the real register and verification flow and clinicians through the provisioning CLI, and assert side effects on real infrastructure (mailpit messages and their lack of PHI, episode and escalation rows read as the image superuser, ciphertext at rest, zero foreign rows under solace_app, Alertmanager emails), never just HTTP status. Progress is tracked in tests/e2e/expected_failures.yaml as strict xfail with the expected failing hop; a listed test that passes early or fails at a different hop blocks the barrier.

Wave proof: each wave's acceptance suites are written in phase A from the frozen interfaces and must fail for the documented reason before phase B. W0: boot/migrate smoke in dev and strict, plus the crisis E2E red at documented hops in dev. W1: crisis delivery over REST and WS in both profiles, fault injection (graph exception, notification outage, SMTP rejection, Kafka down at boot, LLM failure, safety-service down, duplicate detections, unacknowledged re-page) and the negative-phrase E2E, plus crisis-path alerts reaching mailpit. W2: chat journey, restart durability, encryption at rest, contract suite, identity sessions. W3: deletion completeness across every store, isolation matrix, audit tamper detection and concurrency, PHI capture scan, secrets injection, consent gate, OAuth against the stub IdP. W4: MFA, password reset, restore drill with measured RPO/RTO, alert firing, RS256-only and per-service-key rejection. W5: release gate twice on ENVIRONMENT=production from a git-archive export of the final checkpoint tree.

Barrier order: every unit suite (one process each), then realinfra suites (at most 2 concurrent), then the wave's e2e suites, then the review package, then bug-finding rounds until one is dry (at most 3). CI mirrors the unit, contract, image build/boot and migrate layers; because nothing is pushed, 'make ci-local' is the proof until the owner commits.

## 8. Risks

- Clinical sign-off (D-05, D-06, D-22, D-28, D-29) may lag engineering. W1 proceeds on conservative defaults with the owner's acceptance recorded, but W5 and go-live block without a named clinician approver, and a late lexicon change re-runs the phrase suite across five detectors.
- Without BAAs for Portkey/Anthropic or the SMTP relay (D-04, D-12), LLM layers stay disabled for real users and alerts cannot carry user identity. The product must remain safe and usable with templates and deterministic screening, and the pilot's value may shrink.
- A recall-first lexicon can flood clinicians with false positives, and clinicians who learn to ignore pages defeat the safety path. Controls: the negative phrase set, ELEVATED-means-resources-only, per-episode coalescing, acknowledgement and monitoring of page volume.
- The IF-01 bootstrap is the largest design risk: all nine services adopt it in W0, so a defect cascades everywhere. Mitigations: Opus design, AGY adversarial review before phase B, behaviour-preserving adoption, the conformance test and boot smoke in both profiles.
- Running as solace_app with RLS from W0 will surface failures in flows without request context (registration, consumers, reapers, CLIs). Without acting_as_user discipline and realinfra tests, these fail silently as empty reads.
- In one shared working tree, a half-finished phase-A platform edit breaks every lane's tests, and a missed handover (the user-service split files, slot files) produces silent edit conflicts. Mitigations: phase gating, the pre-dispatch disjointness check, owning-suite runs per task, full regression only at barriers and rollback.ps1 per declared paths.
- Docker capacity: two concurrent full stacks (about 15 containers each) can exhaust RAM; the plan relies on at most 2 e2e lanes, Weaviate disabled by default and stack reuse within a lane.
- The working tree stays uncommitted until the owner acts (D-17). One destructive git command could lose weeks of work; checkpoint trees are the only safety net, and MVP-008 cannot close without the owner's commit.
- No-commit-on-failure consumer semantics risk poison-message loops and head-of-line blocking of crisis alerts; bounded in-place retries, the malformed-message DLQ path and realinfra poison tests are mandatory.
- langgraph-checkpoint-postgres is not installed locally and uses psycopg rather than asyncpg; its pinned DDL (including CREATE INDEX CONCURRENTLY) must be applied through slot 017 correctly, or checkpoint durability (MVP-066) slips. D-20 approval is a W0 entry dependency.
- W2 is the largest wave (about 90 issues across 12 workstreams), and the 6-implementer cap makes it the long pole; low/medium domain items are already deferred to W5, and further slips need explicit owner acceptance.
- AWS deployer permissions are blocked (D-25), so the release gate may be provable only on the local strict profile, leaving TLS/ACME, DNS, host alarms and S3 backups unproven on the real host.
- The mobile client currently targets Supabase and mocks (D-11); if it is not re-pointed at IF-12, the hardened backend contract goes unused in the pilot.
- E2E flakiness under timing (Kafka rebalance, SMTP retries, re-page intervals) could mask real failures or block barriers; deterministic fakes, shortened configurable intervals, bounded generous waits and the twice-green release rule are the controls.
- Erasure versus duty-of-care retention (D-24) is a legal question: pseudonymizing crisis episodes and escalation records may conflict with counsel's view in either direction.
- Two refusals still skip the screen (crisis-review residual): WS frames over 8 KB (WS-11.17) and REST bodies over 4000 characters (422, WS-11.4). A long crisis message gets no resources and no page. This is raised for the D-22 sign-off: either accept it, or screen the first 4000 characters before refusing.
- From W2, the WS-11.7 thread-ownership lookup sits on the chat path, so a Postgres outage refuses the turn before the screen runs. WS-10's crisis path is designed to stay live during a database outage (the in-band resources need no database). Executors should keep the lookup after the screen, or fail open to the local screen, and the W2 Postgres-outage E2E (WS-05.8) must cover it.
- No commits (D-17) leaves the working tree as the only full copy, and checkpoint trees are unreferenced git objects that git gc can prune after about two weeks. Mitigation: each barrier tree is exported with git archive to a zip outside the repo and copied off the machine by the owner. The owner may also approve git config gc.pruneExpire never for the program's duration (OPEN-ITEMS X-11). Never run git clean, reset or checkout in this tree.
- AWS provisioning is blocked: the existing user MedCodex-Local can only call Bedrock (IAM simulation of 2026-10-19). If the deployer policy is not attached before W4, the off-host backup target is unproven; if not attached by W5 entry, the release gate stops (D-25). The owner action is X-01.
- The venv baseline may differ from the 5,377 anaconda baseline (shadowed or upgraded packages, PyJWT >= 2.13). W0 entry records the per-suite venv baseline, and any drop needs a ledger Ruling before tasks start (D-20).
- Bedrock model availability and quotas for the chosen Anthropic model in us-east-1 are unverified. BEDROCK_MODEL_ID is set at deploy after checking ListFoundationModels and inference profiles, and LLM features stay off for real users until the AWS BAA is recorded (D-04, X-02, X-08).
- Multi-country (D-29): users from a country without verified resources would get only the generic fallback. Mitigation: pilot admission stays a named cohort (D-31), and each new locale needs clinician-verified resources before its users join (X-09).
