## Step 3: implementation

- `01-roles.sh` defines a local `_solace_file_env NAME` helper. It reads `NAME` or `NAME_FILE`; when both or neither are set, or the file is unreadable or empty, it prints `01-roles.sh: error: ...` naming the variable to stderr and exits 1. It never prints a value or path.
- The roles are then created by `psql -v ON_ERROR_STOP=1 --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" --set=app_password=... --set=migrator_password=...` with a quoted heredoc. The heredoc uses `:'migrator_password'`, `:'app_password'` and `format(... current_database()) \gexec` for `ALTER DATABASE ... OWNER TO solace_migrator`, `REVOKE ALL ... FROM PUBLIC` and `GRANT CONNECT, TEMPORARY ... TO solace_migrator, solace_app`, then runs `REVOKE CREATE ON SCHEMA public FROM PUBLIC`.
- Roles: `solace_migrator` LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION BYPASSRLS; `solace_app` LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS.
- Safe whether sourced or executed: plain POSIX, no `local`, no `set` changes, only `_solace_*` names, an explicit `|| _solace_fail` on psql, and the two password variables plus the helper functions are unset at the end.
- Additions beyond the brief's sketch, all fail-closed or leak hardening:
  1. `SET log_statement='none'; SET log_min_duration_statement=-1; SET log_min_error_statement=panic;` before the password-bearing statements. RED showed why this is needed: the server logs `STATEMENT: <full text>` for a failing statement, so a failed `CREATE ROLE ... PASSWORD` would otherwise leave the password in the container log.
  2. `-v VERBOSITY=terse` and `--no-psqlrc`, so a psql error never prints `LINE 1:` statement context.
  3. A guard that refuses `POSTGRES_DB` empty, `postgres`, `template0` or `template1`. Without it, an unset `POSTGRES_DB` would hand the ops maintenance database to the migrator.
- `tests/migrations/conftest.py` (per Produces):
  - `PgServer(host, port, superuser_password, app_password, migrator_password)`, with the passwords excluded from the repr; `dsn()` percent-encodes user, password and database. `superuser_dsn`, `migrator_dsn` and `app_dsn` all default to `solace`.
  - `start_postgres(*, env, tls_dir=None, tls_mode=None)` returns a started `PostgresContainer`. It mounts init-db read-only, defaults `POSTGRES_USER=postgres` and `POSTGRES_DB=solace`, and removes the container if start fails. For WS-02.5, `tls_dir` or `tls_mode` mounts `scripts/db/pg_tls_entrypoint.sh` at `/usr/local/bin/solace-pg-entrypoint.sh`, mounts `tls_dir` read-only at `/run/secrets`, sets `SOLACE_PG_TLS=<tls_mode>`, uses entrypoint `sh <wrapper>` with command `postgres`, and raises `FileNotFoundError` while the wrapper does not exist yet.
  - The readiness probe is overridden. The stock testcontainers probe runs `PGPASSWORD='<pw>' psql` through docker exec and repeats the command in its TimeoutError text. The override uses a credential-free `pg_isready` on 127.0.0.1, which the init-time server does not listen on, and fails fast with a log tail if the container exits during init.
  - `pg_server` (session) generates passwords with `token_urlsafe(18)`, plus `"m/@#:%" + token_urlsafe(12)` for the migrator, and waits until the host port is reachable.
  - `fresh_database` (function) creates `solace_test_<hex>` with OWNER solace_migrator and applies the same REVOKE, GRANT and schema REVOKE. It asserts that owner, `datacl`, public-schema owner and `nspacl` are identical to `solace`, then drops the database `WITH (FORCE)`. Admin SQL goes through synchronous psycopg, so it stays outside the test's event loop.
  - `insert_minimal(conn, table, **values)` reads `information_schema.columns` and skips nullable, defaulted, identity and generated columns. It covers uuid, text types (truncated to the length limit and unique), ints, numeric, floats, bool, json and jsonb, timestamp and timestamptz, date, time and timetz, interval, bytea, inet and cidr, arrays and enums. It raises a clear error for an unknown table, column or type.
  - `require_docker()` skips, or fails when `SOLACE_REQUIRE_REALINFRA=1`.
  - Registers the `realinfra` marker, so `--strict-markers` (pytest.ini addopts) does not reject it.

## Concerns

1. **Deviation from the verbatim test (teardown only):** `test_mvp_249_init_fails_closed_without_role_passwords` calls `container.remove(force=True, v=True)` where the brief has `remove(force=True)`. Without `v=True`, every run leaks the image's anonymous `/var/lib/postgresql/data` volume, which would accumulate on CI and break the "tear down volumes" rule. The assertions are unchanged.
2. **Compose breaks until WS-03.2 lands (hand-off).** On an empty volume, `docker-compose.yml` postgres (POSTGRES_USER `solace`, init-db mounted) now fails closed with `SOLACE_APP_PASSWORD or SOLACE_APP_PASSWORD_FILE must be set`. The old SQL worked there only because the compose superuser happened to be named `solace`. WS-03.2 must pass `SOLACE_APP_PASSWORD` and `SOLACE_MIGRATOR_PASSWORD` (or `_FILE`) and keep `POSTGRES_DB=solace`. Existing dev volumes are unaffected, because init runs only on an empty data directory, so they keep the old nine databases and no roles until recreated. WS-05's `INIT_DB_ENV` must use the same names (R-02.12).
3. **CRLF risk for `01-roles.sh` (hand-off; `.gitattributes` is not my file).** The repo has `core.autocrlf=true` and no `.gitattributes`. A Windows checkout of this file from git would get CRLF, which breaks both the `#!/bin/sh` exec path and the sourced path. The working-tree file is LF and the index stores LF. Recommendation: add `*.sh text eol=lf` (also needed for WS-02.5's `pg_tls_entrypoint.sh` and `docker/entrypoint.sh`).
4. Not done, outside scope: `PUBLIC` still has the default CONNECT and TEMP on the `postgres` maintenance database, so `solace_app` can connect there (it holds no data). The brief only scopes `solace`. Revoking it would be a one-line follow-up if D-02 wants it.
5. Passwords reach psql as `--set` argv, as the brief prescribes, so for the few milliseconds of init they are visible in `/proc/*/cmdline` to root and postgres inside the container. They are never logged.
6. For WS-02.5: `from conftest import start_postgres` resolves to this module only while it is the last-imported rootless conftest. That holds when running `tests/migrations` alone, which is how the plan runs it. A combined `tests/` run might resolve `conftest` to another directory's module.
