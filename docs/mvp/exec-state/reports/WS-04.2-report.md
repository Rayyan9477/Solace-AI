### 3. R-01.2 is applied here (WS-01 to WS-04 request, needed by WS-01.6)
- Routing `uvicorn.error` to the root logger at NOTSET would undo uvicorn's `--log-level warning`. It would then log WebSocket handshake lines (`"WebSocket /ws?token=..." [accepted]` and the 403 lines) with the token in the query string.
- So `uvicorn.error` is held at `max(spec level, WARNING)`. It still propagates to the JSON handler, as the brief says.
- Cost: uvicorn's INFO startup lines ("Uvicorn running on ...") are no longer logged; the runtime logs its own startup.
- WS-01.6's WS-handshake conformance assertion is not written yet; the behaviour probe covers this behaviour for now.

### 4. Choices beyond the brief's literal text, all stricter or neutral
- **`cache_logger_on_first_use=False`.** The old per-service chains used True. With caching, a logger first used under an earlier configuration keeps that chain, and with it a replaced stdout. Without caching, every reconfigure (dev to strict, tests, later bootstrap calls) reaches every logger. The cost is a few cheap object allocations per log call.
- **The root handler writes to the current `sys.stdout`.** It is a `StreamHandler` over a tiny proxy that looks up `sys.stdout` on every write. The output is identical to `StreamHandler(sys.stdout)`, but a replaced stdout (pytest capsys, a re-opened stream) never leaves the root logger writing to a closed file. One consequence: `handler.stream` is the proxy, not `sys.stdout` itself, which matters if WS-04.5 checks identity.
- **Library loggers.** Routed loggers get `disabled = False` and lose uvicorn's own handlers. `uvicorn.access` also gets `propagate = False`, so re-enabling it cannot leak query strings into the JSON stream.
- **Unknown `log_level`.** It falls back to INFO with one warning instead of raising.
- **`StartupDependencyError` redacts `scheme://...` text from `reason`.** This enforces the "reason never carries a secret or URL" contract by construction. Reasons without a URL pass through unchanged.
- **The missing `bootstrap` names raise `AttributeError` until WS-04.3**, so the error reads "cannot import name ..." (see `__init__.py` above).
- **Strictness checks either side** (controller note): `is_strict_environment(spec.environment) or is_strict_environment()`. WS-04.3 and WS-04.4's briefs key strictness on `is_strict_environment(spec.environment)` alone. The same either-side rule should probably be applied there (or promoted to one shared helper), so a strict bare `ENVIRONMENT` with an unset or misnamed `*_ENVIRONMENT` cannot skip the secret validation. This is WS-04.1's concern 4.

### 5. Sanitizer behaviour observed (owned by WS-09, not changed here)
- **Recursive log line.** `phi_sanitizer_processor` logs its own `phi_detected` line (count and types only, no values) from inside the chain. It prints just before the line that triggered it. No recursion loop occurs, because that line holds no PHI.
- **Partial masking.** The mask keeps the e-mail domain and the last four phone digits, for example `j*******@example.com ******5309`.
- **Source lines in tracebacks.** A traceback includes the source line of the `raise`, and the sanitizer sees that text too.
- WS-09's W3 `LogEventSanitizer` hardening is where these belong.

### 6. Stdlib records don't carry the logger name or contextvars
This follows the brief's `foreign_pre_chain` exactly: no `add_logger_name`, no `merge_contextvars`. Request ids bound by WS-04.3 therefore appear on structlog lines but not on uvicorn, aiokafka or asyncpg lines. Add them to `foreign_pre_chain` if operators need them.

### Fix-round concerns
1. **Basic/Bearer false positives.** Because of `(?i)` plus `{8,}`, the specified pattern also rewrites ordinary prose, for example `"basic configuration loaded"` becomes `"basic [REDACTED] loaded"` (or `"bearer tokens ..."`). I kept the pattern exactly as specified. Tightening it (for example requiring a digit, `=`, `+` or `/` in the credential, or a case-sensitive `Bearer`/`Basic`) is a reviewer call.
2. **The canary logs one `phi_detected` line at strict startup.** It carries only `count=2` and `types=["email","phone"]`, and goes through whatever structlog config is active before `configure`. 3. **The canary checks only the structlog-side sanitizer object.** The stdlib chain uses the same function object, so one check covers both.
4. **Non-string values bypass redaction and the sanitizer.** These are exception objects, custom reprs, and the tuple and list items that `JSONRenderer` stringifies. Per your note, this is WS-09.13's. `redact_credentials` does walk dicts, lists and tuples of strings.
5. **`handleError` ignores `logging.raiseExceptions`.** It always writes the fixed `log_record_dropped` line, which is the point: a dropped record stays visible without its content.
