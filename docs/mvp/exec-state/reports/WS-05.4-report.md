## Deviations (for the controller)
1. **The mailpit CA, cert and key are generated in both profiles, not only in strict.**
   - The single overlay mounts mailpit's pair as compose file secrets from `${SOLACE_SECRETS_DIR}`, matching
     WS-03.2's per-file pattern. So the files and `SOLACE_SECRETS_DIR` must exist in dev too.
   - Dev mailpit does not use them: its `MP_SMTP_TLS_*` and `MP_SMTP_REQUIRE_STARTTLS` are
     `${E2E_SSL_CERT_FILE:+...}`, which is empty in dev.
   - The Postgres TLS files are generated in strict only.
2. **Generator rules beyond the brief's table.** The registry has grown since the brief, and without these the
   generator exits 2 on the real registry.
   - `USER_SERVICE_FIELD_ENCRYPTION_KEY` → urlsafe32.
   - `LLM_ANTHROPIC_API_KEY` → unset (D-04: the overlay pins it `""`).
   - `AUTH_PRIVATE_KEY_PEM` → unset (unused while HS256; the W4 RS256 cut-over must add a rule).
   - In strict, required non-secret sources without a strict default (`DOMAIN`, `CADDY_ADMIN_EMAIL`) get the
     registry `example`, so `${X:?}` passes.
   - Extra outputs: `E2E_BASIC_AUTH_PASSWORD` (the plaintext of the bcrypt hash, cost 10, for harness use) and
     `REDIS_URL`.
   - Keys are the registry **source** names, because e2e.env is compose interpolation. A row with no source uses
     its name.
3. **`--certs-cmd`: the brief's hint `echo` is not used.** There is no `echo.exe` on PATH on this Windows host.
   The test instead passes a fake gen_certs script that writes the three IF-22 names. That is stronger: it checks
   the renames to `e2e-ca.crt`, `mailpit.crt` and `mailpit.key`.
4. **`EMAIL_SMTP_TLS_MODE: ${E2E_SMTP_TLS_MODE:?...}`** (fail fast) instead of a bare `${E2E_SMTP_TLS_MODE}`. In
   the mailpit allow-list, compose needs `$$` for the anchor.
5. **`sql()` uses `WITH t AS (<query>) SELECT coalesce(json_agg(t),'[]'::json) FROM t`** instead of a FROM
   subquery, so `UPDATE ... RETURNING` works (the verify_email_via_sql shortcut needs it). psql reads the query on
   stdin: psql does not interpolate variables in `-c`.
6. **`start_stack` extras.**
   - A `config --quiet` precheck runs before any build.
   - It removes any stale project by label first, because old volumes hold old passwords.
   - On failure it tears down unless keep or reuse is set. reuse means "reuse the env and skip `--build`".
   - **Manifest-driven tolerance:** a service may stay down at the 180 s deadline only while
     `expected_failures.yaml` has an active (not due) entry for
     `test_mvp_039_call_reaches_each_service[<svc>]` at hop `service_live` for this profile. The deadline still
     applies to that service, so a slow service is never misreported as down.
   - This is what makes part 2's plan work: only that case XFAILs. Without it every test would fail at
     `stack_up`.
7. `kafka_lag` returns `{topic: lag summed over partitions}`; a partition with no committed offset counts its
   whole log.
8. `make_user(role != "user")` raises, because the public route creates users only; use `provision_clinician`.
9. **The ps1 delegates to `python -m solace_testing.e2e`** so there is only one compose command. Its parameters
   are named `-E2EProfile`/`-E2EEnvironment` because `$PROFILE` is a PowerShell automatic variable.
10. **The self-test overlay test is extended.**
    - Every base/prod service's non-environment keys may differ only in the reset keys.
    - No `container_name` or `env_file` is left, and only caddy, mailpit and fake-llm publish, on ephemeral
      127.0.0.1 ports.
    - The first test also asserts `ps` is non-empty, so `all()` cannot pass vacuously.

## Modes and owners (HAR-1, POSIX; Windows uses the directory ACL)
| File | Mode | Owner | Read by |
|---|---|---|---|
| `DIR`, `DIR/secrets` | 0700 | generating user | host only. A bind-mounted file is reached through its mount point, so the 0700 parents do not block containers |
| `DIR/.solace-e2e-run`, `DIR/e2e.env` | 0600 | generating user | host only (compose reads e2e.env on the host) |
| `e2e-ca.crt` | 0644 | generating user | the nine app services, as appuser uid 1000 |
| `postgres-ca.crt` | 0644 | generating user | the nine app services and migrate, as appuser uid 1000 |
| `server.crt` | 0644 | generating user | postgres TLS wrapper, as root |
| `mailpit.crt` | 0644 | generating user | mailpit, as root |
| `server.key` | 0600 | generating user | postgres TLS wrapper, as root. It copies the key to a postgres-owned 0600 file before stepping down (verified: the postgres image's User is empty) |
| `mailpit.key` | 0600 | generating user | mailpit, as root (verified: the image config has no User and the entrypoint is `/mailpit`) |

**Caveat:** under rootless or user-namespaced Docker, container root is not host root, so a 0600 key owned by the
runner would not be readable. That is outside the current CI assumption (rootful Docker) and is documented in the
generator docstring.
