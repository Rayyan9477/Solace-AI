## Root cause
1. `phi_sanitizer_processor` calls `PHISanitizer.sanitize_dict`, which calls `PHIDetector.detect` for each string value.
2. When `detect` found something, it logged `phi_detected` through **structlog**, which runs the same chain again.
3. `merge_contextvars` put the bound request context back into that line. The sanitizer flagged the same bound value again and logged `phi_detected` again, and so on until `RecursionError`.

The traceback cycle at RED was `phi_protection.py:438 phi_sanitizer_processor -> :348 sanitize_dict -> :274 detect (logger.info) -> chain -> :438`.

The stdlib path broke as well. `logging.StreamHandler.emit` re-raises `RecursionError` and does not pass it to `handleError`. So a plain `logging.getLogger(...).error(...)` whose message holds PHI, logged while PHI-looking context was bound, raised out of the caller too. That includes uvicorn, aiokafka and service loggers.

## Fix (phi_protection.py only)
- Added a module-level `_phi_sanitizing: ContextVar[bool] = ContextVar("_phi_sanitizing", default=False)`.
- **`phi_sanitizer_processor`:**
  - If the guard is already set, it returns `event_dict` unchanged (the brief's pass-through).
  - Otherwise it does the existing lazy init of `_structlog_sanitizer`, sets the guard (`token = _phi_sanitizing.set(True)`), sanitizes, and resets the guard by token in `finally`.
  - Sanitizing is synchronous and has no `await`, so the flag cannot be seen by another task. Each thread has its own context.
- **New `_log_detection(count, phi_types)`**, called from `detect`:
  - Inside sanitization (guard set), the counter goes to the **stdlib** logger `solace_security.phi_protection` at **DEBUG**. The message is `"phi_detected count=%d types=%s"`, with sorted type names joined by commas. It carries no value.
  - Outside the chain (service code calling `detect`, `mask_phi` or `PHISanitizer` directly), the counter is still the structlog INFO line `phi_detected count=.. types=[..]`, as before. The only change there is that `types` is now sorted. That line goes through the chain once and is sanitized once: the nested detection on its bound context drops to the stdlib DEBUG counter.
- I kept the names `phi_sanitizer_processor` and `_structlog_sanitizer`. `logging_chain_names()` and `test_strict_rejects_an_inactive_sanitizer` depend on them.
- The WS-04.2 strict canary still passes. `_assert_sanitizer_active` calls the processor directly, the guard is set and reset inside that call, and the canary event comes out masked (`j*******@example.com ******5309`).

## Deviations from the brief
1. **Case 2 uses seeded uuid4 values instead of `uuid.uuid4()`.** The values are `uuid.UUID(int=random.Random(0).getrandbits(128), version=4)`, which are valid version-4 UUIDs. With truly random ids, about 3.8% of runs would contain no flagged id, so the test would sometimes not exercise the bug. Seed 0 gives 4 flagged ids out of 200 (3 driver's-licence matches and 1 credit-card match). The test asserts that at least one id is flagged.
2. **I added tests 3 to 9** for the other paths this bug reaches: direct `detect` callers, stdlib records, the DEBUG counter, the canary, the pass-through, the reset after an exception, and asyncio isolation.

## Concerns
1. **The pass-through is safe only while nothing logs bound context during sanitization.**
   - Under the guard, a nested event is returned unsanitized. Today the only nested line is the stdlib DEBUG counter, which holds counts and type names. The runtime `foreign_pre_chain` has no `merge_contextvars`, so that record carries no bound context.
   - If a future change adds `merge_contextvars` to the stdlib `foreign_pre_chain`, the DEBUG counter would carry raw bound context out.
   - Tests 4[DEBUG] and 5 run at DEBUG and assert that no raw id appears, so they would catch that change.
2. **The guard lives in `phi_sanitizer_processor`.** A custom processor that called `PHISanitizer` or `PHIDetector` directly would still recurse. No such processor exists in the repo today: every service `main.py` and the runtime chain use `phi_sanitizer_processor`.
3. **Behaviour change for WS-04.2.**
   - Inside the chain, the `phi_detected` counter is now stdlib DEBUG. Before, it was a structlog INFO line printed before the triggering line. So at INFO it no longer appears.
   - The note at line 176 of `D:\tmp\mvp-exec\reports\WS-04.2-report.md` ("logs its own phi_detected line ... No recursion loop occurs") is now out of date. Its no-recursion claim was also wrong whenever the bound context looked like PHI.
4. **Correlation loss (not in scope).** Bound ids that look like PHI are masked in logs, so they no longer correlate across lines. For example, `123456789` becomes `***-**-6789`, and about 1 in 61 uuid4 `user_id` values lose part of their text. WS-04.3 re-mints request ids for this reason. Pattern hardening for uuids (MVP-189) belongs to the later WS-09 work.
5. **The checkpoint tree includes other lanes' work.** It snapshots the whole working tree, including files other implementers are editing in parallel.

### Fix
- **The nested path masks and never logs.**
  - Added a module-level `_nested_sanitizer: PHISanitizer | None`, plus `_nested_source`, which records the `_structlog_sanitizer` that `_nested_sanitizer` was copied from.
  - The new helper `_quiet_copy(sanitizer)` returns `PHISanitizer(PHIDetector(settings.model_copy(update={"log_detections": False}), patterns))`. That is the outer sanitizer's own settings and patterns with detection logging off.
- **`phi_sanitizer_processor` now works like this:**

### Round-2 concerns
1. **Nested events get no `phi_detected` counter.** This is deliberate: a counter from the nested path is exactly what could re-enter the chain. The outer event's counter still goes to stdlib DEBUG.
2. **The guard still leaks into `call_soon` callbacks scheduled while it is set.** Python copies the context when it schedules the callback. The effect is now harmless: the callback's lines are masked by the nested sanitizer, and its own `detect` calls send their counter to stdlib DEBUG instead of structlog.
3. **A local part over 64 characters keeps up to 7 leading characters visible**, because the match now starts within 64 characters of the `@`. The old pattern showed 1. The rest of the address is masked. This is the accepted cost of the coordinator's pattern, which has no leading `\b`. A TLD over 24 letters is no longer matched as an e-mail address.
4. `_quiet_copy` reads `_detector._settings` and `_detector._patterns`. Those are private attributes, but they belong to this same module.
