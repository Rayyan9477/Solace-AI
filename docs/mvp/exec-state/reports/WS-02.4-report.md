## Step 3: implementation (`scripts/db/migrate.py`)

**CLI**
- Usage: `python -m scripts.db.migrate {upgrade,downgrade,current} [target] [--wait-timeout SECONDS (120)] [--lock-timeout SECONDS (600)] [--expected-role NAME (solace_migrator)]`.
- Exit codes: 0 success; 1 failure; 2 usage (argparse errors, no database URL, unusable URL).
- `downgrade` requires an explicit target, and `current` takes none. Both are refused with exit 2.
- stdout holds only `migrated: <version or base>`, plus Alembic's own `current` line.
- Progress and errors go to stderr, prefixed `migrate:`. Alembic's INFO lines come from `logging.config.fileConfig(alembic.ini, disable_existing_loggers=False)`, the same as the alembic CLI.

**URL resolution: `resolve_database_url(environ)`**
- It reads the given mapping only.
- `DATABASE_URL` wins when it is non-empty (stripped). `DATABASE_URL_FILE` is left to docker/entrypoint.sh, as the brief says, and the exit-2 message names both.
- Otherwise, when `POSTGRES_PASSWORD` is set, it builds the URL from `PostgresSettings(_env_file=None, ...)` using POSTGRES_HOST, _PORT, _DATABASE and _USER or their defaults. User, password and database are percent-encoded, and an IPv6 host is bracketed.
- Otherwise it returns None.
- Invalid `POSTGRES_*` values raise `MigrateUsageError` naming the variable, never its value.
- Accepted schemes: `postgresql://`, `postgres://` and `postgresql+asyncpg://`. Each is normalized to `postgresql://` for asyncpg and env.py.

**Steps, each fail-closed**
1. **Wait.** asyncpg login attempts, each with a timeout of at most 10s, every 0.5s until `--wait-timeout`. Only transient failures are retried: OSError other than `ssl.SSLError`, TimeoutError, `CannotConnectNowError`, `TooManyConnectionsError` and `PostgresConnectionError`. A refused login (`InvalidAuthorizationSpecificationError`, which includes a bad password and a missing hba entry) fails at once with `login refused for <redacted>`. Other errors (missing database, TLS) fail at once with `cannot connect to ...`. A timeout gives `database not reachable at <redacted> within Ns (k attempt(s); last error: ...)`.
2. **Role preflight (the WS-02.3 review hand-off).** One `pg_roles` query covers the expected role and both platform roles:
   - `current_user` must equal `--expected-role`, otherwise: `refusing to migrate: connected as postgres (a superuser), but migrations run only as solace_migrator, a NOSUPERUSER role (IF-03)`.
   - Both platform roles must exist and carry init-db's security attributes:
     - `solace_migrator`: NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION BYPASSRLS
     - `solace_app`: NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS
   - No checked role may be a member (`pg_has_role(..., 'MEMBER')`) of a SUPERUSER role.
   - `solace_app` may also not be a member of any BYPASSRLS role, which covers `GRANT solace_migrator TO solace_app`.
   - A custom `--expected-role` must still be NOSUPERUSER, so `--expected-role postgres` is refused.
   - Every problem is listed in one message, for example: `refusing to migrate: role solace_migrator must be NOCREATEDB (it is CREATEDB); role solace_app must be NOREPLICATION (it is REPLICATION); role solace_app must be NOBYPASSRLS (it is BYPASSRLS)`.
   - LOGIN is deliberately not checked, so ops may set `solace_app` NOLOGIN during an incident.
3. **Lock.** `SELECT pg_try_advisory_lock(hashtext('solace_migrate'))` on that connection, every 0.5s until `--lock-timeout`. One `waiting up to Ns for the migration lock ...` note is printed. A timeout gives `could not take the migration lock (...) within Ns: another migrate job still holds it`.
4. **Alembic.** `_run_alembic` runs `alembic.command.upgrade|downgrade|current` in a worker thread through `asyncio.to_thread`, because env.py calls `asyncio.run`:
   - It sets `DATABASE_URL` in `os.environ` for the duration and restores it afterwards. env.py reads only that variable, and env.py is not my file.
   - A process-wide `threading.Lock` serializes in-process callers, because Alembic's `context` proxy is process-global.
   - The Config is built from alembic.ini's `[alembic]` section, re-escaped for interpolation, with an absolute `script_location`. It deliberately names no config file, so env.py skips `fileConfig`. Otherwise every logger already present in an in-process caller would be disabled (WS-05's fixtures).
   - The thread is shielded: if the run is cancelled, it still waits for the thread to end before releasing the lock. A second cancellation stops the wait.
5. **Result.** It reads `alembic_version` on the lock connection: a comma-joined value, or None for base. It releases the lock; on failure it only notes this, because the server drops the lock with the connection and the command's own outcome must not be masked. It closes the connection, or terminates it if close fails. The CLI then prints `migrated: ...`.

**Python API**
- `run_migrations(database_url, command, target="head", *, wait_timeout_s=120.0, lock_timeout_s=600.0, expected_role="solace_migrator") -> str | None` runs `asyncio.run(migrate_async(...))`. Inside a running event loop it raises `RuntimeError` pointing at `migrate_async`.
- `async def migrate_async(...)` takes the same parameters.
- Also exported: `resolve_database_url`, `redact`, `MigrateError` (exit_code 1) and `MigrateUsageError` (exit_code 2).
- Alembic's own errors propagate unchanged; a probe confirmed `alembic.util.exc.CommandError`.

**Redaction**
- `redact(url)` returns `user:***@host:port/db`. The query string, which may carry `password=`, is never shown. A URL that does not parse (bad port, no scheme or host, empty) becomes `<unparseable database URL>`.
- Every printed message (MigrateError text, and the Alembic or driver traceback on exit 1) is scrubbed of every form of the password: raw, unquoted, quoted, `%%`-escaped, from userinfo even when the URL does not parse, and from the query. The full URL is scrubbed too.

1. **The preflight is stricter than the brief's single check.** Per the review hand-off it requires the full init-db attribute set and no privileged memberships. I have not verified RDS's rules for this; it is not relevant to the current compose or EC2 staging plan.    - `ssl.SSLError` is already treated as non-transient (fail fast).
   - env.py's engine needs its own `connect_args`.
   - URL query parameters such as `sslmode=` reach both asyncpg and SQLAlchemy as they are; I have not tested that.
6. **For WS-05 (R-02.4):**
   - Call `run_migrations` from sync code or a thread. An async session fixture must `await migrate_async(...)`, because `run_migrations` raises inside a running loop.
   - In-process runs serialize on a process lock and briefly set `os.environ["DATABASE_URL"]`; another thread reading it during a run sees the migrator URL.
   - Progress notes go to stderr even for API callers.
7. **For WS-01.9 (migrate image) and WS-03.2 (compose):**
