## Defect
The fix-1 settle phase was capped at `deadline + settle`. A match recorded after `timeout` needs quiet until `last_match + settle`, which is later than that cap, so the call raised "did not read to the end offsets of the first match". It did so even though the end offsets had been reached, for example when a duplicate arrived inside the first match's window but after the deadline, or under a steady stream of matches. It failed loud (no false pass), but the cause it reported was wrong.

## Design (the coordinator's "extend the window from the last match, bounded" option, keeping the reviewer's honest messages)
- Every match, including one after `timeout`, restarts the `settle` quiet window. The call returns only once a full `settle` window passes with no new match and the consumer has reached the end offsets seen at the first match. A returned list is therefore always followed by `settle` quiet seconds plus a full drain, so R2's guarantee is unchanged: no duplicate within `settle` of the latest match is missed.
- The settle phase is bounded at `first_match + timeout + settle` (previously `deadline + settle`). A late first match, or a duplicate after the deadline inside the first window, therefore always gets its full window and is returned. The call lasts at most about `2 * timeout + settle`.
- At the bound it raises rather than returning a count that may be short, and names the real cause:
  - drained but a window still open: `matches on '<topic>' were still arriving Ns after the first one (k so far, the latest x.xxs ago); pass a larger timeout or a narrower predicate`;
  - end offsets not reached: `k match(es) on '<topic>', but it did not read to the end offsets of the first match within Ns of it`.
- The no-match path (R3) is untouched: `[]` is returned only after reading to the end; otherwise `did not read ... to its end`.
- The docstring describes exactly this.
