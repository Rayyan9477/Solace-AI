## What was implemented

### `metrics.py`
- Module-level metric objects on `prometheus_client.REGISTRY`, with the names and labels the interface gives:
  - `HTTP_REQUESTS` (`solace_http_requests_total{service,route,method,status}`)
  - `HTTP_DURATION` (`solace_http_request_duration_seconds{service,route}`)
  - `READINESS_CHECK_OK` (`solace_readiness_check_ok{service,check}`)
  - `SERVICE_READY` (`solace_service_ready{service}`)
  - `BACKGROUND_TASK_UP` (`solace_background_task_up{service,task}`)
  - `CRISIS_DETECTED` (`solace_crisis_detected_total{source,level}`)
  - `LLM_FALLBACK` (`solace_llm_fallback_total{service,reason}`)
  - `AUDIT_WRITE_FAILURES` (`solace_audit_write_failures_total{service}`)
- `register_metrics_route(app)` adds `GET /metrics`, which returns `generate_latest(REGISTRY)` as `CONTENT_TYPE_LATEST`. The route is left out of OpenAPI.
- A small `_metric` helper reuses the existing collector if the module is imported a second time (a reload, or a second package path). Without it, that import fails with "Duplicated timeseries".

### `health.py`
- `@dataclass(frozen=True) CheckResult(ok, critical, detail)` and `ReadinessReport(ready, checks)`.
- `register_health_routes(app)` adds three routes. All are out of OpenAPI, and all read `app.state.runtime` and `app.state.spec` at request time, so the module does not import `bootstrap`.
- `GET /live`:
  - 200 `{"status":"alive"}`, also when no runtime exists yet.
  - 503 `{"status":"dead","task":name}` for the first registered task that has exited.
- `GET /ready` and `GET /health`:
  - Body: `{status, service, version, checks:{name:{ok,critical,detail}}}`.
  - 200 when ready; 503 `not_ready` when a critical check fails.
  - 503 `not_ready` with `checks:{}`, and `solace_service_ready` set to 0, when `app.state.runtime` is missing.

### `http.py`
**`RequestContextMiddleware`** is pure ASGI. It handles `http` and `websocket` scopes and passes `lifespan` through.
- **Ids:**
  - `X-Request-ID`, `X-Correlation-ID` and `X-Turn-ID` are each accepted only if they `fullmatch` `[A-Za-z0-9._:-]{1,128}`. It uses `fullmatch` because `$` would also accept a trailing `\n`.
  - Otherwise a `uuid4()` is minted.
  - The ids are stored on `scope["state"]`.
  - The context is cleared first (`clear_correlation_ids()` and structlog `clear_contextvars()`), then `set_correlation_ids(...)` is called and the ids are bound into structlog contextvars.
  - Both are cleared again in `finally`.
- **HTTP response:**
  - The three ids are added as response headers. Any copy the route set itself is replaced, so there are no duplicates.
  - Metrics use the route template: `scope["route"].path`, or for plain Starlette routes such as `/openapi.json`, a lookup by endpoint, else `__unmatched__`.
  - One `http_request` line is written with service, method, route, status and `duration_ms`. It is DEBUG for `/live`, `/ready`, `/health` and `/metrics`, INFO otherwise, and never contains the raw path or query.
- **Status recorded** is the status that was sent. If an exception escapes before a response starts, it is 500; if the client went away (cancelled), it is 499.

**`install_exception_handlers(app, spec)`**:
- `RequestValidationError`: 422 `{error:{code:"VALIDATION_ERROR", message:"Request validation failed", details:[{field,message,type}], request_id}}`.
- `ValueError`: 400 `{error:{code:"BAD_REQUEST", message:"Invalid request", request_id}}`, plus one `request_value_error` INFO line with the class name.
- Any other `Exception`: 500 `{error:{code:"INTERNAL_ERROR", message:"An unexpected error occurred", request_id}}`.
  - It reads the ids from `request.state` and adds them as response headers.
  - It logs one `unhandled_exception` line with the ids, class name and traceback. The traceback goes through the WS-04.2 PHI sanitizer chain.
- `WebSocketRequestValidationError`: the WebSocket is closed with 1008 and a fixed reason. FastAPI's default puts the errors, input values included, into the close reason.
- `HTTPException` keeps FastAPI's `{detail}` body (D-11; WS-04.9 changes this in W2). `spec` is accepted and unused until then.
- No body ever contains `str(exc)`.

**Edge CORS:**
- `cors_allowed_origins(spec)` reads the comma-separated `CORS_ALLOWED_ORIGINS`. In strict, an empty value, `*` or `null` raises `StartupDependencyError("cors", ...)`.
- `install_cors(app, origins)`:
  - Credentials are allowed only for an explicit origin list.
  - Methods are GET, POST, PUT, PATCH, DELETE and OPTIONS; `allow_headers=["*"]`.
  - The exposed headers are the three ids plus the orchestrator's current list (X-Session-ID, X-Thread-ID, Retry-After, X-RateLimit-*).

**Strictness:** `spec_is_strict` is re-exported from `logging._is_strict`. That keeps one rule for the whole runtime: strict when the spec environment OR the bare `ENVIRONMENT` is strict, as the controller decided.

### `bootstrap.py`
**`ServiceRuntime(spec)`** has `spec` and the five component attributes, all `None` at first: `pg_pool`, `redis`, `event_plane`, `service_tokens`, `phi_codec`.
- `register_readiness_check(name, check, *, critical=True)` replaces any check with the same name and invalidates the cache.
- `register_background_task(name, task)`:
  - Sets the gauge and adds a done callback. When the task exits, the callback sets the gauge to 0 and logs one `background_task_exited` line: the outcome, plus class name and traceback for an error.
  - A registration that is not a running task (already finished, or `None`) counts as dead at once.
- `register_shutdown(name, closer)` appends to an ordered list for WS-04.4's `stop_service_runtime`.
- `outbound_headers()` returns `get_correlation_headers()`.
- `dead_background_task()` backs `/live`.
- `async evaluate_readiness()`:
  - Runs every check at once, each under `asyncio.wait_for(..., READINESS_CHECK_TIMEOUT_SECONDS=2.0)`.
  - Any failure, including a timeout or a malformed return, gives `detail=type(exc).__name__`.
  - A returned detail is capped at 200 characters, with `scheme://...` replaced.
  - The report is cached for `READINESS_CACHE_SECONDS = 2.0`. Concurrent calls share one run through an `asyncio.Lock`, so a public `/ready` cannot be used to multiply datastore probes. A generation counter stops an evaluation that started before a new registration from caching an out-of-date report.
  - Sets `READINESS_CHECK_OK` and `SERVICE_READY`.

**`create_service_app(spec, *, lifespan, routers, title)`**, in order:
1. Resolves the CORS policy first, so a bad strict config fails before an app exists.
2. Decides docs: `docs_enabled`, or "not strict" when it is None.
3. Sets the httpx/httpcore WARNING floor (concern 2).
4. Builds `FastAPI(...)`. `debug` is never set, because FastAPI's debug mode renders tracebacks to clients.
5. Sets `app.state.spec = spec`.
6. Installs the handlers.
7. Registers `/live`, `/ready`, `/health` and `/metrics` before the service routers, so a router cannot shadow them.
8. Adds the routers.
9. Adds `RequestContextMiddleware`, then CORS last, so CORS is outermost.

A comment marks where WS-04.6 inserts `install_rate_limiting` (before `RequestContextMiddleware`, which makes it inner).

## Concerns

### 1. HIGH, needs the WS-09 owner: the PHI log sanitizer recurses forever on any bound context value it flags
**The bug:**
- `PHIDetector.detect` (`src/solace_security/phi_protection.py:273-278`) logs `phi_detected` through structlog from inside the processor chain.
- `merge_contextvars` puts the bound context back into that event.
- So if any contextvar value matches a PHI pattern, every log call in that context recurses until it hits `RecursionError`.

**Examples that trigger it:**
- a 9-digit number (the "SSN without dashes" pattern);
- `a1234567` (the driver's licence pattern);
- about 1 in 61 random `uuid4` strings: the first group is a letter and 7 digits, or the last group is 3 letters and 9 digits.

**Proof:** `D:\tmp\mvp-exec\ws04\ws043_phi_recursion_probe.py` uses only the WS-04.2 chain and gets `RecursionError` for `a1234567`, `123456789` and a UUID ending `abc123456789`. It works for `probe-1`.

**Impact:** a request whose ids trip it fails at its first log line. That includes the crisis path, and a single crafted header (`X-Request-ID: 123456789`) is enough.

**What I did, in my file only:**
- An inbound id that the sanitizer's `DEFAULT_PATTERNS` would flag is replaced.
- A minted id is re-minted until it is clean. I checked 20,000 minted ids and all were clean.
- This also keeps ids unmasked, so they still correlate across log lines.

**What is still exposed:** every other contextvar. A `user_id` UUID bound by the auth layer or a service would break all log lines for about 1 in 61 users.

**Fix needed:** a re-entrancy guard in `phi_protection.py`, for example no `phi_detected` logging while the processor is running, or a contextvar flag. This should land before the W0 phase-B adoptions start binding more context.

### 2. Placement of the httpx URL floor (controller or WS-04.2 owner)
- The brief's access-line test caught that the WS-04.2 chain prints httpx's INFO `HTTP Request: GET http://.../items/abc?token=s3cr3t "HTTP/1.1 200 OK"` line through the root JSON handler.
- In production, every outbound service call would log its full URL, query string included.
- I fixed it in my files: `http.quiet_outbound_url_logging()` raises `httpx` and `httpcore` to at least WARNING, and `create_service_app` calls it.
- The right home is `logging.configure_service_logging`, next to the `uvicorn.access` silencing. Right now a process that configures logging but never builds an app (a worker or a CLI) is not covered.
- Suggest moving it there and keeping the http.py helper as a no-op alias, or deleting it.

### 3. The brief's dead-task test registers `None`, not a task
- `TestClient.portal.call(lambda: asyncio.ensure_future(...))` returns `None`, because anyio awaits any awaitable the callable returns.
- The test passes because a registration that is not a running task counts as dead. That is fail-safe: a caller who registers `await task` by mistake sees `/live` 503.
- The test still does not exercise a real finished `Task`. The behaviour probe does: a real task that raises is detected, its gauge goes to 0, and its exit is logged.
- Suggested test fix: create the task inside a coroutine, `async def mk(): return asyncio.ensure_future(asyncio.sleep(0))`, then `c.portal.call(mk)`.

### 4. Strictness helper
- `http.py` imports the package-private `logging._is_strict` and re-exports it as `spec_is_strict`, so the runtime has one either-side rule.
- WS-04.4 should import `spec_is_strict` from `http` rather than re-implementing it, or the WS-04.2 owner could make it public.

### 5. Choices beyond the brief's literal text (stricter or neutral)
**Request ids and metrics:**
- PHI-like ids are rejected and re-minted (concern 1).
- Methods outside GET/HEAD/POST/PUT/PATCH/DELETE/OPTIONS share the label `OTHER`, so a client cannot grow the metric's cardinality.
- A client that disconnects before any response is recorded as 499, so it does not count as a 5xx.

**Validation details:**
- `field` is the `loc` joined with dots, `body.` prefix included.
- Any part that is not an identifier, such as a client-supplied dict key that could be an e-mail address, becomes `[key]`.
- `message` is pydantic's schema-built text, except for `value_error`, `assertion_error` and custom error types: their text comes from the validator author and may quote the input, so they get "Invalid value".
- At most 50 details are returned.

**Error handling:**
- The WebSocket validation handler is replaced, because FastAPI's default echoes input values in the close reason.
- The `ValueError` handler re-raises for WebSocket scopes, so the default handling is unchanged there.
- The 500 handler logs `unhandled_exception` with the ids and the traceback. uvicorn also logs its own "Exception in ASGI application" traceback, which has no ids, so production gets two tracebacks per 500.
- The 500 response carries the id headers. Starlette's `ServerErrorMiddleware` sits outside our middleware, so the handler has to add them itself.

**Readiness and tasks:**
- Concurrent `/ready` calls share one evaluation, behind a lock with a generation guard.
- A returned detail is URL-redacted and capped.
- A malformed return counts as a failed check.
- Background-task exits are logged and set the gauge from a done callback.

**WebSockets:** a WebSocket scope gets ids and contextvars, but no metrics, no access line and no response headers.

**CORS:**
- Strict also rejects `null`.
- A dev `*` turns credentials off; with credentials on, Starlette would reflect any caller's origin for cookie requests.
- An empty dev list allows no origin. The orchestrator's current expose list is kept, so its adoption does not lose headers.

**Context clearing:** the whole structlog context is cleared at the start and end of each request, so anything inner code binds lasts only for that request.

**Metrics registration:** the duplicate-import fallback in `metrics._metric` reads `REGISTRY._names_to_collectors`, which is private to prometheus_client.

### 6. For WS-03 and the deploy owners
- On edge services, `/metrics` (no auth) and `/ready`, which names the checks, are public unless Caddy blocks them.
- CORS preflights are answered by the outer CORS middleware, so they get no ids and no metrics. This is the order the brief asks for.
- Starlette sends 500 bodies from outside CORS, so a browser on an edge origin sees a CORS error instead of the 500 envelope. This is how Starlette works today.

### 7. Not mine, noted for WS-07
The middleware resets the correlation ids but not the RLS `current_user_id`. Leaks between requests are prevented only because uvicorn gives each request its own context copy.

### Concerns after fix round 2
1. **Open, WS-04.2 / logging owner: uvicorn's "Exception in ASGI application" line.**
   - That line, routed through `uvicorn.error`, prints `str(exc)` for every exception that reaches the server.
   - For a `ValidationError` that means stored patient text. A `ValidationError` raised outside route handling (a middleware such as the W1 rate limiter, or a WebSocket route, where `_value_error_handler` re-raises) still leaks this way, as the `/mw` probe row shows.
   - For any other exception, the line duplicates the runtime's `unhandled_exception` traceback, without request ids.
   - Suggested fix in `logging.py`: drop that record, or strip its `exc_info`. The runtime already logs every 500 with ids, and `ValidationError`s safely.
2. **The `origin` of a `ValidationError` is pydantic's frame.** The innermost Python frame is in pydantic (for example `pydantic/main.py:...:model_validate`), not the service code, because the raise happens in pydantic-core. The `route` field on the same line still locates the fault. If a service-code frame is wanted, pick the innermost frame outside the pydantic package.
3. **`origin` carries absolute file paths** (for example `/app/services/...` in images). There is no PHI in them, but they reveal the source layout to anyone who can read the logs.
