## What was implemented

### `datastores.py`
- `redis.asyncio` is imported at module level as `redis_asyncio`, and `ConnectionPoolManager` is a module attribute, so the fakes can patch both.
- **`component_start_failed(runtime, component, exc)`** is the single wrapper. Bootstrap can reuse it for the W1 to W3 components.
  - Strictness uses `http.spec_is_strict`, the either-side rule.
  - **Strict:**
    - Logs one ERROR `runtime_component_failed`.
    - Raises `StartupDependencyError(component, reason) from None`. The reason is the exception class name. For a missing variable it is fixed text, `"REDIS_URL is not set"`.
    - The original exception is not chained, because its text can carry a DSN or password. The probe confirms the formatted traceback has no secret and the context is suppressed.
  - **Otherwise:**
    - Logs one WARNING `runtime_component_degraded`.
    - Registers a critical readiness check named after the component, which returns `(False, <class name>)`.
  - **Fields on both lines:** `component`, `error` (class name), `cause` (class of `__cause__`/`__context__`, when present), `origin` (basename:line:function of the raise), and `setting` for a missing variable. Exception text never appears.
- **`start_postgres(spec, runtime) -> asyncpg.Pool | None`:**
  - Registers the `postgres` closer (`ConnectionPoolManager.close_all_pools`) before the attempt. Every pool the process opened is closed at shutdown, including after a failed start.
  - Calls `ConnectionPoolManager.get_pool("default")`.
  - In strict, calls `_schema_head_check(pool)`.
  - On success it registers the critical `postgres` check. Failure goes through `component_start_failed`, called outside the `except` block so the strict error has no context.
- **`_schema_head_check(pool)`:**
  - Imports `assert_schema_head` from `solace_infrastructure.database.schema_check` at call time, and is called only in strict.
  - It also compares the returned revision with `SCHEMA_HEAD` and raises `SchemaVersionMismatch` itself. `assert_schema_head` decides strictness from the bare `ENVIRONMENT` alone, so without this a spec-only-strict mismatch would only warn. The probe covers both cases.
- **`start_redis(spec, runtime)`:**
  - Reads `REDIS_URL` and never logs it. An unset value raises `DatastoreSettingMissing("REDIS_URL")`.
  - Builds the client with `from_url(url, decode_responses=True, socket_connect_timeout=5.0, socket_timeout=5.0)`.
  - Then sends `PING`, bounded at 10 s.
  - On success it registers the `redis` closer (`client.aclose`) and the critical `redis` check. On failure it closes the client first.
- **Readiness checks (`_DatastoreCheck`):**
  - The startup connection counts as the first probe.
  - A live probe (`pool.fetchval("SELECT 1")` / `PING`) runs again only when the last result is older than `DATASTORE_PROBE_INTERVAL_SECONDS = 5.0`.
  - A failed probe reports the class name only.
  - A probe cut off by the 2 s readiness timeout records nothing, so the next evaluation probes again.
  - Why it works this way: the brief's fake `Pool` has no methods, yet `report.ready` is asserted right after start. It also means `/ready` traffic cannot probe a datastore more than once per 5 s.

### `bootstrap.py`
- **Constants:** `SHUTDOWN_STEP_TIMEOUT_SECONDS = 5.0`, `READINESS_REFRESH_SECONDS = 15.0` and `READINESS_REFRESHER_TASK = "readiness_refresher"`. Both timing constants are read at call time, so they can be monkeypatched.
- **`required_secrets_for(spec)`:** `AUTH_SECRET_KEY`, plus `POSTGRES_PASSWORD` when the spec uses Postgres, `REDIS_URL` when it uses Redis, and `ENCRYPTION_MASTER_KEY` and `ENCRYPTION_SEARCH_HASH_SALT` when it handles PHI.
- **`start_service_runtime(app, spec)`**, in order:
  1. `ProductionGuards.assert_startup(spec.environment, service_name=..., required_vars=required_secrets_for(spec))`.
  2. `configure_service_logging(spec)`.
  3. `start_postgres` when `uses_postgres`, then `start_redis` when `uses_redis`.
  4. The readiness refresher.
  - It then sets `app.state.runtime` and logs `service_runtime_started`.
  - If anything after the guards and logging raises, including a strict `StartupDependencyError`, it runs `stop_service_runtime` over what was already registered and re-raises.
- **Readiness refresher:**
  - A task registered with `register_background_task`, so its death shows on `/live`.
  - Every `READINESS_REFRESH_SECONDS` it calls `runtime.evaluate_readiness()`, which re-probes the datastores and keeps `solace_service_ready` / `solace_readiness_check_ok` current.
  - A failed evaluation logs `readiness_refresh_failed` with the class name and the loop continues. A readiness bug therefore cannot turn `/live` red and get the container restarted.
  - Its closer, registered last, cancels it and waits for it.
- **`stop_service_runtime(runtime)`:**
  - Runs the closers last-registered first.
  - Each one runs as a task bounded by `asyncio.wait(timeout=SHUTDOWN_STEP_TIMEOUT_SECONDS)`. On timeout it is cancelled and not waited for, so a closer that swallows cancellation cannot hold up the rest.
  - A step that raises, times out, or is not awaitable (a sync closer gives `TypeError`) is logged as `runtime_shutdown_step_failed` with `step` and `error` (class name only), and the next step still runs.
  - Each outcome is retrieved, so an abandoned closer never logs "exception was never retrieved" with its text.
  - It ends with one `service_runtime_stopped` line that carries `failed_steps`.
  - Closers run once: a second call does nothing.
  - Only cancellation of the caller propagates.
- **Resulting teardown order:** refresher, then redis, then postgres. In W1, closers registered later (`event_plane.stop`) run before the pool closes, as WS-04.6 requires.
