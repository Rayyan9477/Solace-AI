## What was implemented (`production_guards.py`)
- Module-level `is_strict_environment(env: str | None = None) -> bool`. When `env` is None it reads `ENVIRONMENT`, defaulting to `development`. It strips and lower-cases the name, then tests membership in `STRICT_ENVIRONMENT_NAMES = {"production", "staging"}`.
- `DEFAULT_REQUIRED_IN_STRICT = ("AUTH_SECRET_KEY", "ENCRYPTION_MASTER_KEY", "ENCRYPTION_SEARCH_HASH_SALT", "POSTGRES_PASSWORD")`. `REQUIRED_IN_PRODUCTION` is now this tuple. `FORBIDDEN_VALUES` is keyed on these four names.
- `validate_environment(*, required_vars=None)`:
  - The required set is the caller's names (de-duplicated, order kept), or the default when None.
  - Forbidden-value checks run only for names in that set.
  - The Postgres checks run only when `POSTGRES_PASSWORD` is in the set. They require `POSTGRES_SSL_MODE == "verify-full"` and reject a superuser `POSTGRES_USER` (postgres, admin or root).
  - The retired `ENCRYPTION_KEY` length check now applies to `ENCRYPTION_MASTER_KEY` (at least 32 characters), and only when that name is required.
- `assert_startup(service_environment, *, service_name=None, required_vars=None)` runs the consistency check, then passes `required_vars` through to `validate_environment`.
- `assert_environment_consistency` behaves as before, but uses `is_strict_environment` on both sides. The `STRICT_ENVIRONMENTS` class attribute is gone; nothing referenced it.
- Every violation string starts with `"<NAME> "` and contains no value. This also covers the debug flags and `POSTGRES_USER`, which used to echo their values. The `production_security_validation_passed` log line now records `checks_passed` (the names of the checks that ran) and `required_vars` (variable names only).
- `__all__` adds `is_strict_environment`, `DEFAULT_REQUIRED_IN_STRICT` and `STRICT_ENVIRONMENT_NAMES`.

## Concerns
1. **Deploy-facing behaviour change (coordinate with WS-03 and WS-02).**
   - In staging and production, all ten services now require `AUTH_SECRET_KEY`, `ENCRYPTION_MASTER_KEY`, `ENCRYPTION_SEARCH_HASH_SALT` and `POSTGRES_PASSWORD`, plus `POSTGRES_SSL_MODE=verify-full`. No compose file or `.env.example` sets `POSTGRES_SSL_MODE` today.
   - `infrastructure/aws-staging/DEPLOY.md:99` still describes `require` as the floor. A strict deploy without `verify-full` (and a CA and host name Postgres can verify) will now fail loud at startup. That is intended under D-15, but the deploy config and runbook must match.
   - Services that do not read the encryption secrets (for example analytics) still need them until their mains pass `required_vars` (WS-04.5 / `required_secrets_for`).
2. **Lint on the verbatim test file.** ruff reports I001 (no blank line between `import secrets` and `import pytest`) and N802 (`test_is_strict_environment_reads_ENVIRONMENT_when_none`). I left the brief's text untouched. If CI lints tests, it needs a `# noqa: N802` or a rename, plus an import-grouping fix.
3. **Markers are not registered.** `realinfra` and `e2e` are not in pytest.ini; that is WS-01.4's job. The gate reads markers by name, so it works now. But under the default addopts (`--strict-markers`), later bootstrap tests that use these markers will fail at collection until WS-01.4 lands.
4. **Pre-existing gap, not in this brief.** Strictness for the secret checks comes from the bare `ENVIRONMENT`. If `ENVIRONMENT` is unset while the service's own `*_ENVIRONMENT` says production, the consistency check is a no-op ("either side unset"), so the secret validation is skipped. I suggest the runtime bootstrap (WS-04.2/04.4, `ServiceRuntimeSpec.environment`) validates whenever either side is strict.
5. **`ENCRYPTION_MASTER_KEY` length.** The guard keeps an "at least 32 characters" floor, re-targeted from the dead `ENCRYPTION_KEY` check. `EncryptionSettings` itself requires exactly 32 bytes, while the brief's fixture and the documented recipe use `token_hex(32)`, which is 64 characters. That conflict is MVP-092 (FP-N-14) and outside this task. The guard accepts both forms.
6. **Choices beyond the brief's literal text**, all stricter or neutral:
   - Whitespace-only values count as unset.
   - Forbidden values are compared after strip and lower-case.
   - A bare `str` passed as `required_vars` raises `TypeError`; otherwise it would be iterated one character at a time.
   - `required_vars` is de-duplicated, order kept.
   - `""` was dropped from the `POSTGRES_PASSWORD` forbidden list, because the required check already covers it and the same problem would otherwise be reported twice.
   - `POSTGRES_SSL_MODE` must equal `verify-full` exactly, with no case folding.
   - An unset `POSTGRES_USER` is accepted, because the `PostgresSettings` default user is `solace`, a non-superuser.
7. **Kept as is.**
   - The `assert_environment_consistency` message still includes the two environment names. They are not secrets, and the brief says that method keeps its behaviour.
   - The `ProductionSecurityError` text still says "production" even when staging fails. This is cosmetic.
8. **Environment note.** The venv was created with `include-system-site-packages = true`, so pytest and pytest-asyncio load from the anaconda base. That held throughout; nothing was installed.
