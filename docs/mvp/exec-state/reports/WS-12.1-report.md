### Lifespan composition (inside the runtime bracket, in the brief's order)

1. `settings = SafetyServiceAppSettings()`; `strict = is_strict_environment(settings.environment)`.
2. `get_safety_config()`. The detector comes from `build_crisis_detector(safety_config)` and the repository from
   `build_escalation_repository(runtime.pg_pool, environment=settings.environment)`. The escalation manager is
   `EscalationManager(EscalationSettings(...), repository=repo)`.
3. `await initialize_event_publisher()`, then `SafetyService(...)`. Next come
   `runtime.register_shutdown("safety_service", safety_service.shutdown)` and
   `runtime.register_shutdown("event_publisher", event_publisher.stop)`, then `await safety_service.initialize()`.
4. The PHI-encryption block, unchanged except for `is_strict_environment(settings.environment)`.
   `configure_phi_encryption` is still called, and safety stays in `_PHI_ENCRYPTING`.
5. `_require_event_delivery_in_strict(settings)`, then the `app.state` assignments.
6. When `settings.kafka_enabled`, the lifespan calls `initialize_notification_bridge(kafka_settings=KafkaSettings(bootstrap_servers=...), use_mock=settings.kafka_use_mock, postgres_pool=runtime.pg_pool)`.
   - Strict: there is no `except`, so a bridge failure fails the boot.
   - Dev/test: a failure logs WARNING `notification_bridge_unavailable` with `error_type` only (no exception text).
     It also registers the readiness check `event_bridge` (critical), which returns `(False, "unavailable")`.
   - On success: `runtime.register_shutdown("notification_bridge", bridge.stop)`.
7. `yield`. Closers run in reverse order: bridge (its outbox poller, then its publisher), then the event
   publisher, then the service, then the runtime's own closers (refresher, Redis, Postgres).

## Crisis path (controller requirement)

`test_ws_12_1_crisis_check_in_the_adopted_app_reaches_the_safety_outbox` runs the real adopted `main.app`
(SAFETY_KAFKA_ENABLED=true, mock producer, no Postgres or Redis reachable, so the runtime degrades and
`runtime.pg_pool` is None). It checks:

- the bridge, publisher and service stops are runtime shutdown closers, registered so that the stop order is
  bridge, then publisher, then service;
- the lifespan started the bridge and its outbox poller;
- `POST /api/v1/safety/check` with "I want to kill myself" returns `is_safe=False`, and it writes a
  `safety.crisis.detected` outbox row for that user whose `source_service` is exactly `"safety-service"` (the
  value `KafkaEventBridge` passes to `create_publisher`);
- the poller drains that row to the broker;
- after the lifespan exits, the bridge and poller are stopped.

Postgres was not available here, so the test checks owner stamping on the in-memory store
(`InMemoryOutboxStore(source_service="safety-service")`). With a pool, the same `source_service` goes to
`PostgresOutboxStore`, which refuses a foreign or blank owner (WS-06.1). That path is not exercised here
(no real infra).

`test_ws_12_1_strict_bridge_failure_stops_the_boot` runs the real composition in production against a
stand-in runtime that has a pool. A bridge start failure propagates (the boot fails); the publisher and
service closers still run, in that order; no readiness check hides the failure.

`test_ws_12_1_dev_bridge_failure_makes_the_service_unready` sets dev/test and makes the bridge fail with a
URL that carries a secret. `/ready` answers 503 with `event_bridge = {ok: false, critical: true, detail: "unavailable"}`,
the secret appears in no response, and `/live` answers 200.

## Concerns

1. **Staging boot is now strict.** Staging fails closed on: no Kafka (`SAFETY_KAFKA_ENABLED` must be true),
   a failed PHI-encryption setup, a failed bridge start, no Postgres, and (deviation 1) no Redis.
   `docker-compose.yml` sets `SAFETY_KAFKA_ENABLED: "true"`. The healthchecks probe `/live` (Dockerfile and compose).
2. **Old `/health` body.** `/health` now mirrors `/ready`; it used to return a fixed 200 body. Smoke test R-12-9
   (WS-05) needs updating, as noted above.
3. **Event-loop-bound singletons (existing issue, not changed).** `events._publisher` and
   `event_bridge._notification_bridge` are module singletons, and the publisher's `asyncio.Queue` binds to the
   first event loop. A second lifespan in the same process (TestClient suites, an in-process restart) would make
   `SafetyEventPublisher._process_events` log errors in a loop and dispatch nothing. One lifespan per process in
   production is fine. My tests reset both singletons. A per-lifespan publisher would fix it (WS-12 or WS-06 follow-up).
4. **Partial bridge start is not undone (existing issue in `event_bridge.py`, WS-06 owns it).**
   `KafkaEventBridge.stop()` acts only when `_started` is set. If the producer starts and then `ensure_table`
   or the poller start fails, the producer is never stopped. In strict the process exits; in dev a producer leaks.
5. **The poller's death is invisible.** The outbox poller task is not a registered runtime background task, so
   `/live` would not report it dead. Its loop catches every `Exception`, so it does not die in practice. The W1
   event plane is the natural owner.
6. **WS-12.17 is not needed by this adoption.** The lifespan builds no `ContraindicationRepository` (D-19), and
   no code in this adoption opens a private pool. The private pool in `infrastructure/database.py`
   (`create_pool`) is still there for WS-12.17.
7. **Exception text in the PHI block.** The block keeps `str(e)` in its warning and in the strict
   `RuntimeError` message, as the brief said (WS-12.12 removes it in W3).
8. **Strictness reads one source.** Safety's own checks use `is_strict_environment(settings.environment)`,
   following the brief. The runtime is strict when either the spec environment or the bare `ENVIRONMENT` is
   strict. `ProductionGuards.assert_startup` already rejects a strict mismatch, so in practice the two agree.
