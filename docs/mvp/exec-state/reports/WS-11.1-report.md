### WS111-CRI-1: fail open on limiter backend errors

Change, under the controller's one-file grant: in `src/solace_security/rate_limit.py`, `RateLimitMiddleware.dispatch` now wraps the limiter check-and-increment (`check_request_async`, or the sync `check_request`) in `try/except Exception`. On an error it logs `rate_limiter_backend_error` with `error_type=<exception class>` only (no key, IP, user, path or message text) and returns `await call_next(request)`. A limiter that answers "not allowed" is still a 429. `CancelledError` is not caught (it is a BaseException). The module docstring records the rule.

- Metric: none. The module exposes no metric, so per the ruling I added none and no new metrics dependency (importing the runtime's metrics would make `solace_security` depend on `solace_infrastructure`). The W1 work (D-26, WS-07 / WS-11.3) can add the counter.
- Tests, in `services/orchestrator_service/tests/test_mvp_016_runtime_adoption.py`, against the real orchestrator app in development with auth and the graph stubbed:
  - `test_mvp_016_limiter_backend_outage_fails_open_on_the_chat_route`: `redis.asyncio.from_url` returns a client whose `eval`/`ttl` raise `redis.exceptions.ConnectionError`. POST `/api/v1/orchestrator/chat` gives 200 with the graph's reply. Exactly one `("warning", "rate_limiter_backend_error", {"error_type": "ConnectionError"})` is logged (via a recording logger patched onto the module).
  - `test_mvp_016_a_real_over_limit_still_returns_429`: a healthy fake Redis whose counter is 10000 gives 429 `RATE_LIMIT_EXCEEDED` with `Retry-After >= 1`.

### WS111-SPE-1: socket timeouts on the W0 limiter's Redis client

`main.RATE_LIMIT_REDIS_TIMEOUT_SECONDS = 0.5`. `_register_rate_limiting` builds `redis_asyncio.from_url(redis_url, decode_responses=True, socket_connect_timeout=0.5, socket_timeout=0.5)`. Chosen values: 0.5 s connect and 0.5 s per command, the controller's default (the brief names none). The runtime's own client uses 5.0 s, which is too long in front of the 2 s safety-check budget. A hung or blackholed Redis now costs a chat request about 0.5 s, then the limiter fails open.

- Test `test_mvp_016_limiter_redis_client_has_socket_timeouts`: `app.state.rate_limit_redis.connection_pool.connection_kwargs` carries both timeouts at 0.5.
