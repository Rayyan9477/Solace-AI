## Concerns / hand-offs

1. **`update_preferences` default-create (security review).** The existence check runs under the caller's context; only the save is wrapped in `acting_as_user(user_id)`. Every current caller passes the authenticated user's own id (`/users/me/preferences`), so the context already matches. A future cross-user caller (an admin or service route) would hit this sequence:
   - RLS hides the existing row;
   - the INSERT … ON CONFLICT (user_id) DO UPDATE, running as the target user, resets the target's preferences to defaults;
   - the subsequent UPDATE then fails.

   Flag for WS-14.8/14.20.
2. **Consent document version (MVP-220).** The version is no longer bound anywhere. `_row_to_entity` still reads the integer lock `version`, so `get_by_user_id` raises a ValidationError on real PG. This is deliberately left: it is WS-14.11/14.12's RED.
3. **PII in errors and logs (WS-14.5).** `create_user` returns, and logs as `user_creation_failed`, the raw asyncpg text. The RED output showed it includes the failing row: email and the email verification token. `user_saved_postgres` and `verification_email_send_error` also log the email.
4. **The TLD knob is not refused in staging/production.** The strict e2e profile may need it. It logs a WARNING when active. If the controller wants a strict-env refusal, it is a one-line check in `allow_special_use_tlds`. The variable is not in `deploy/env/env-contract.yaml`; that is the pending WS-05.4 part 2 overlay / `OVERLAY_ALLOWED_KEYS` hand-off.
5. **Misleading encryption metadata.** `users.encryption_algorithm` keeps its server default `AES-256-GCM` while `encryption_key_id='none'`. The metadata claims AES until WS-14.10's codec.
6. **Lazy database connection.** The repositories now connect only on the first query (`get_pool` on first acquire). Without Postgres the lifespan still starts, as it effectively did before. WS-14.2 adds the fail-loud datastores.
7. **Leftover test config.** `services/user-service/tests/conftest.py` still sets `USER_DB_PASSWORD`, and `config.DatabaseConfig` still requires it. WS-14.2 drops both.
