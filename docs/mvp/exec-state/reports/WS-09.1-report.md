## Step 3: implementation (encryption.py)
- New `parse_master_key(value: str, *, strict: bool) -> bytes`. Formats are checked in the brief's order:
  1. `base64:` + `base64.b64decode(..., validate=True)` that decodes to exactly 32 bytes.
  2. `re.fullmatch(r"[0-9A-Fa-f]{64}")` decoded with `bytes.fromhex`.
  3. Only when `strict` is false: a value whose UTF-8 encoding is exactly 32 bytes, used as-is.
  Anything else raises `ValueError` with the brief's message verbatim (a fixed module constant). The message never contains the value, its length or a fragment, and the raise uses `from None`.
- New private `_strict_environment()`: `os.environ.get("ENVIRONMENT", "development").strip().lower() in {"staging", "production"}`.
- `EncryptionSettings`:
  - `model_post_init` stores `parse_master_key(..., strict=_strict_environment())` in the `PrivateAttr` `_master_key_bytes`.
  - The new read-only property `master_key_bytes` returns it, and fails closed with the same message if it was never populated.
  - `for_development()` now raises `RuntimeError` in staging as well as production.
  - `model_config` gains `hide_input_in_errors=True`, so no `ValidationError` from this settings model echoes input values (key material). Without this the never-echo test cannot pass.
- `KeyManager.__init__`: `self._master_key = self._settings.master_key_bytes`. For legacy raw keys this is byte-identical to the old `.encode()`: an ad-hoc check confirmed `KeyManager(s)._master_key == legacy.encode()`. Hex and base64 keys now derive from the decoded 32 bytes.
- Design choices within the brief's wording:
  - A `base64:`-prefixed value never falls through to the legacy raw path, even in dev/test. A declared base64 key that fails to decode is an error, not a silent 32-char raw key.
  - Non-ASCII input to b64decode, and lone surrogates on the legacy path, both raise the fixed message rather than a codec error that would quote the value.

Ad-hoc leak-path probe (throwaway keys, booleans printed only; the scratch script was deleted afterwards):
- A bad key read from the environment in staging is rejected and not echoed.
- `repr`/`str` of the settings show neither the hex key nor the decoded bytes.
- KeyManager uses the decoded bytes.
- Legacy keys stay byte-identical.
- `model_construct()` still fails, because pydantic runs `model_post_init` there too.
- Malformed base64 and surrogate input are rejected cleanly with context suppressed.

## Concerns / follow-ups
1. **ProductionGuards and EncryptionSettings disagree until CR-2 lands (WS-04).** `production_guards._check_encryption_settings` (WS-04.1) still uses a length-only check (`len(value.strip()) >= 32`). In staging/production it therefore passes values that `EncryptionSettings` now rejects: a raw 32-character key, unprefixed base64 (44 chars), or any 32+ character junk. The service would pass the guard and then fail at the PHI-encryption init in `main.py`. That fails closed, but the error comes later and is less clear. CR-2 (WS-04 calls `parse_master_key(value, strict=True)` and reports only the variable name) closes this gap. Note too that the guard `.strip()`s the value but `parse_master_key` does not. A hex key with a trailing newline (for example from a secret file) passes the guard but is rejected here. WS-04 should decide whether to strip before calling `parse_master_key`; I kept the brief's exact matching.
2. **CI and the docs still carry legacy-format keys (CR-1, WS-03).** `.github/workflows/ci.yml` sets a raw 32-character `ENCRYPTION_MASTER_KEY`. That is fine only while CI runs with ENVIRONMENT outside staging/production. `docs/STAGING-BRINGUP.md` still has the `secrets.token_bytes(32).hex()` recipe; it is equivalent and now accepted, but CR-1 asks for the `secrets.token_hex(32)` wording plus the `base64:` alternative.
3. **Behaviour change for staging users of `for_development()`.** It now raises in staging. No service `main.py` calls it (they all use `EncryptionSettings()`), and all test callers run under ENVIRONMENT=test, so nothing in-repo breaks.
4. **`hide_input_in_errors=True` applies to every field of `EncryptionSettings`**, not just master_key. Validation errors for, say, `kdf_iterations` no longer show the bad input. I judged that the right trade-off for a secret-bearing settings model.
5. **Tooling note:** ruff is not installed in the mvp-exec venv, so I ran no lint; per the rules I did not install it.

### Fix
- `EncryptionSettings.__init__(self, **values)` overrides the inherited one as the reviewer specified: `failure = None`; `try: super().__init__(**values)`; `except ValidationError as exc: failure = ValueError("; ".join(e["msg"] for e in exc.errors(include_input=False, include_context=False)))`; then, outside the `except`, `if failure is not None: raise failure`. Because the raise is outside the handler, `__context__` is None. Callers now get a plain `ValueError` with messages only, which still satisfies the existing `pytest.raises(ValueError, match="exactly 32 bytes")` and `pytest.raises((ValidationError, ValueError))` tests. `hide_input_in_errors=True` stays as defence in depth.

The `PrivateAttr` and its import were removed because nothing used them any more.
