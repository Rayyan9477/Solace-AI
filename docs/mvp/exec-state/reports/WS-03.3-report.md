## Deviation 1 (justified, real-infra evidence): the redis command
The brief's verbatim command is `sh -c "umask 077; printf ... > /tmp/redis.conf; exec redis-server /tmp/redis.conf"`. It runs Redis **as root**.
- The image's `docker-entrypoint.sh` drops to the `redis` user (gosu) only when its first argument is `redis-server`. With `sh` as the command it simply execs the shell as root.
- Today's compose (`redis-server --appendonly yes`) does run as `redis`, so the verbatim command would be a privilege regression.
- Evidence: throwaway `docker run` probes of both commands, with the dev default password, containers removed afterwards:
  - verbatim gives `redis-server uid=0`;
  - the fixed command gives `uid=999`;
  - both answer PONG with auth.

The command used:
```
["sh", "-c", "umask 077; printf 'appendonly yes\\nrequirepass %s\\n' \"$$REDIS_PASSWORD\" > /tmp/redis.conf && chown redis:redis /tmp/redis.conf && exec docker-entrypoint.sh redis-server /tmp/redis.conf"]
```
Requirepass is still always on, the password stays off argv (printf is an ash builtin), and the file is 0600, now owned by `redis`. The added real-infra test pins all three. The brief's assertion (`"requirepass" in command`) is unchanged and passes.

### The defect (reproduced by the reviewers, then by the RED below)
`_stop_run` closed `proc.stdout` and `proc.stderr` in a `finally` with no bound. On Windows, `communicate()` reads them in threads. A grandchild that inherited the write ends (the compose plugin) keeps those threads blocked in `read()` while they hold the BufferedReader lock, so `close()` blocks forever and `run()` neither returns nor raises. The KeyboardInterrupt path had the same hang.

### Fix: no shared pipes at all (the reviewers' option 2)
- `run()` now sends the CLI's stdout and stderr to `tempfile.TemporaryFile()` handles and waits only on the CLI process (`proc.wait(timeout)`).
- No reader thread exists, so nothing can block on a lock, and a grandchild holding the inherited file handles is harmless.
- Output is read back from the files.
- `_stop_run` now only does bounded waits:
  1. removes the one-off container;
  2. `wait(grace)`;
  3. `kill()`;
  4. `wait(10)`.

  It returns a note (`" (and the CLI did not exit after kill)"`), which is appended to the raised `ComposeProjectError`. The original timeout error is never masked: the message still starts with "did not exit within Ns".
- The stop grace is the class attribute `ComposeProject.run_stop_grace` (60 s), so tests can shorten it.
