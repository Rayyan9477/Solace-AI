## Canonical lifespan (form (a)), copy exactly

```python
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI

from solace_infrastructure.runtime import ServiceRuntimeSpec, create_service_app, service_runtime

SPEC = ServiceRuntimeSpec(...)


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    async with service_runtime(app, SPEC) as runtime:
        ...  # build the service from runtime.pg_pool / runtime.redis, register readiness checks
        ...  # start consumers / tasks; register EVERY service-owned stop:
        ...  #     runtime.register_shutdown("<name>", <async closer>)
        yield


app = create_service_app(SPEC, lifespan=lifespan, routers=[...], title="...")
```

Rules the conformance check enforces (`_bracket_form` in `tests/bootstrap/test_service_conformance.py`):

- The `async with service_runtime(app, SPEC) as runtime:` is the first and ONLY statement of the
  lifespan body (a docstring may precede it). Exactly one context manager in that `async with`, and the
  target is named `runtime`.
- All composition and the `yield` are inside it. Nothing after the `async with` (no service stop code
  after the `yield`, no trailing statements).
- Service-owned stops go through `runtime.register_shutdown(name, closer)`. Closers run in reverse
  registration order, before the runtime's own (readiness refresher, Redis, Postgres); each is isolated
  (a closer that raises or hangs does not stop the rest).
- The only other accepted shape, form (b), is `runtime = await start_service_runtime(app, SPEC)`
  immediately followed by a `try` (the last statement) that contains the composition and the `yield`,
  whose `finally` is exactly `await stop_service_runtime(runtime)`. Phase B should use form (a).
- Still required as before: no `structlog.configure(`, no `ProductionGuards.assert_startup(`, no
  `exception_handler` in `main.py`.

## Coming in Step 3b (no shape change, but it affects how adopters register tasks)

- LIF-2: `runtime.register_background_task(name, task)` will also register a closer that cancels and
  awaits that task (bounded). Because closers run in reverse order, register a task's graceful stop
  (`runtime.register_shutdown("consumer", consumer.stop)`) AFTER `register_background_task(...)`, so the
  graceful stop runs first and the cancel only mops up.
- LIF-3: a closer that overruns its 5 s step is cancelled and given a 1 s grace to finish its own
  clean-up before the next closer starts.
